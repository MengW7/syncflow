# 项目演示脚本

## 基本信息
- 项目名称：SyncFlow —— CSV 批量导入与任务管理服务
- 演示版本／Git commit：V1.0，标签 `v1.0.0`
- 预计时长：5 分钟
- 演示范围：CSV 导入闭环 —— 创建任务立即返回 → Worker 异步处理 → 成功统计 → 行级错误与文件级错误明细 → 现场改一处业务规则 → 测试证据

## 录制前准备
- [ ] 准备样例文件：`samples/ok.csv`、`samples/row-errors.csv`、`samples/bad-header.csv`（可选 `samples/bom.csv`、`samples/empty.csv`）
- [ ] 确认依赖环境可用：MySQL、Redis、API、Worker、前端五个服务都在跑，`docker compose -f docker-compose.yml -f docker-compose.e2e.yml ps` 里 mysql / redis 为 healthy，api / worker / web 为 Up
- [ ] 确认端口：**本机 8000 落在 Windows 保留区间（`netsh interface ipv4 show excludedportrange protocol=tcp` 显示 7998–8097），所以统一用 18000**。Compose 走覆盖文件：
  ```powershell
  docker compose -f docker-compose.yml -f docker-compose.e2e.yml up -d --build
  ```
  只有宿主机能绑定 8000 时，才按 `README.md` 6.3 用 8000 起宿主机 API 与 Worker
- [ ] 确认只留**一个** Worker：宿主机 Worker 与 Compose Worker 同时消费 `syncflow:jobs` 会把任务标成文件不可读，二者只能留一个
- [ ] 确认 `UPLOAD_DIR` 一致：宿主机起 API/Worker 时都要设 `$env:UPLOAD_DIR = (Resolve-Path .\uploads).Path`；Compose 走容器内的 `/data/uploads`，两边路径不同
- [ ] 确认 `.env` 的 `MAX_RECORDS_PER_JOB` 为 `10000`、`MAX_UPLOAD_FILE_SIZE_MB` 为 `10`
- [ ] 清理上一次演示结果：列表页不留旧任务，`uploads/` 里的历史文件按需删除（保留 `.gitkeep`）
- [ ] 隐藏敏感信息并关闭通知：`.env` 含数据库口令，投屏前不要停留在该文件；关闭 IM / 邮件弹窗
- [ ] 准备对应版本的测试报告：`docs/week-03/测试报告.md`（`65 passed`）与 `docs/week-03/screenshots/` 截图备用
- [ ] 确认浏览器停在 `http://127.0.0.1:5173/jobs/new`，缩放 100%，书签栏收起
- [ ] 按脚本完整预演一次；预演结束后把 `MAX_RECORDS_PER_JOB` 改回 `10000` 并重启 Worker

## 3. 详细分镜脚本

### S01：项目介绍

- 时间：00:00–00:20
- 画面：任务列表页 `http://127.0.0.1:5173`，标题与「创建任务」按钮可见。

#### 操作步骤
1. 展示项目名称 SyncFlow 与页面顶部导航。
2. 打开 `README.md` 首行的版本标签说明，指出本次是 `v1.0.0`。
3. 切换到任务详情页，让观众先看到统计与「查看错误明细」入口的最终形态。

#### 预期画面／结果
- 项目名称、版本 `v1.0.0` 清晰可见。
- 本次演示范围明确：只讲导入闭环，不讲登录、重试、导出。

### S02：环境与数据

- 时间：00:20–00:45
- 画面：终端 A（Compose 状态）、终端 B（探活）、资源管理器或编辑器里的 `samples/` 目录。

#### 操作步骤
1. 在仓库根目录执行 `docker compose -f docker-compose.yml -f docker-compose.e2e.yml ps`，指出 mysql、redis 为 `healthy`，api、worker、web 为 `Up`，api 的端口是 `0.0.0.0:18000->8000/tcp`。
2. 执行探活：
   ```powershell
   curl.exe -s http://127.0.0.1:18000/healthz
   curl.exe -s http://127.0.0.1:18000/readyz
   ```
   指出 `readyz` 的 `data.checks` 里 mysql 与 redis 都是 `ok`（实测返回 `{"status":"ok","checks":{"mysql":"ok","redis":"ok"}}`）。
3. 展示 `samples/` 下五份样例与 `samples/README.md` 的期望统计表。

#### 预期画面／结果
- 五服务状态正常，探活返回 `ok`。
- 观众知道“期望统计”不是临场报数，而是仓库里已有的口径。

### S03：创建并立即返回

- 时间：00:45–01:35
- 画面：创建任务页 `/jobs/new` 与提交后的详情页。

#### 操作步骤
1. 打开 `http://127.0.0.1:5173/jobs/new`，选择 `samples/ok.csv`，指出页面出现「已选择 ok.csv（100 B）」，文件名与大小都对。
2. 任务名称填 `演示-正常`，点击提交。提交期间指出按钮文案变为「正在创建…」且不可点。
3. 请求返回后进入详情页，指出状态徽标是「等待中」或很快变成「处理中」。
4. 在终端补一条计时命令，展示创建接口的响应耗时：
   ```powershell
   $t0 = Get-Date
   $ok = curl.exe -s -X POST "http://127.0.0.1:18000/api/v1/jobs" `
     -F "name=演示-正常" -F "file=@samples/ok.csv;type=text/csv" | ConvertFrom-Json
   "POST 耗时(ms) = " + [int]((Get-Date) - $t0).TotalMilliseconds
   "创建时状态 = " + $ok.data.status
   $okId = $ok.data.id
   ```
   指出状态是 `PENDING`，耗时在百毫秒量级。这条命令会另建一个任务，说明它就是刚才页面那次调用（端到端实测 196 ms，最近复测 108 ms，数量级一致即可，不必念具体数字）。

#### 预期画面／结果
- 创建响应立即返回，`data.status` 为 `PENDING`。
- 详情页显示「正在处理，每 3 秒自动刷新。」
- 页面没有卡在上传等待上。

### S04：成功统计

- 时间：01:35–02:15
- 画面：详情页终态、任务列表页筛选、MySQL 查询结果。

#### 操作步骤
1. 等详情页变成「已完成」，指出总数 2、成功 2、失败 0，结束时间已有，且**没有**「查看错误明细」入口。
2. 回到列表页 `http://127.0.0.1:5173/`，把状态筛选切到「已完成」，指出新任务出现在列表里。
3. 在终端查库，核对写入的两行（`$okId` 就是第 4 步拿到的任务 id；若只走了页面没用终端，把 `$okId` 换成页面上那条任务的 id）：
   ```powershell
   docker compose exec -T mysql mysql --user=syncflow --password=syncflow123 --host=127.0.0.1 syncflow -e "SELECT job_id,external_id,name,amount,record_date FROM sync_records WHERE job_id='$okId';"
   ```
   指出 `external_id` 为大写、金额是两位小数、日期是 `2026-01-01`。

#### 预期画面／结果
- 详情页与列表页都显示 `SUCCESS`、2 / 2 / 0。
- `sync_records` 恰好两行，字段值与样例期望一致。
- 成功任务没有「查看错误明细」入口（反向断言）。

### S05：行级与文件级错误

- 时间：02:15–03:10
- 画面：错误明细页 `/jobs/:jobId/errors`，两张不同的错误表格。

#### 操作步骤
1. 回到创建页上传 `samples/row-errors.csv`，等终态为「部分成功」，指出总数 8、成功 1、失败 7。
2. 点「查看错误明细」，指出行号 3 到 9 与逐行错误码：`FIELD_REQUIRED`、`EXTERNAL_ID_INVALID`、`EXTERNAL_ID_DUPLICATE`、`NAME_TOO_LONG`、`AMOUNT_INVALID`、`DATE_INVALID`、`ROW_COLUMN_COUNT_MISMATCH`。
3. 再上传 `samples/bad-header.csv`，指出终态是「失败」，三个计数都是 0，但**仍然**有「查看错误明细」入口。
4. 打开明细，指出行号显示 `-`、错误码是 `CSV_HEADER_INVALID`；顺便说明 `samples/empty.csv` 同理，码是 `FILE_EMPTY`。
5. （可选）切换到 `bom.csv`，说明带 UTF-8 BOM 的文件同样能导入成功。

#### 预期画面／结果
- `row-errors.csv`：`PARTIAL_SUCCESS`、8 / 1 / 7、7 条明细、错误码逐个对上。
- `bad-header.csv`：`FAILED`、0 / 0 / 0、1 条明细、行号为 `-`。
- 观众能看出“文件级失败”和“行级失败”的区别。

### S06：现场改一处规则

- 时间：03:10–03:55
- 画面：`.env` 编辑器、Worker 终端、创建页与失败详情页。

#### 操作步骤
1. 打开 `.env`，把 `MAX_RECORDS_PER_JOB=10000` 改成 `1`，保存（投屏时不要展示同文件里的口令行）。
2. 重启 Worker，让它重新读配置。**Compose 路径**：
   ```powershell
   docker compose -f docker-compose.yml -f docker-compose.e2e.yml up -d worker
   ```
   用 `up -d` 而不是 `restart`：`env_file` 变了要重建容器，`restart` 沿用旧环境变量。宿主机路径则在 Worker 终端 Ctrl+C 后重新 `python -m app.worker`。
3. 再上传 `samples/ok.csv`：
   ```powershell
   $big = curl.exe -s -X POST "http://127.0.0.1:18000/api/v1/jobs" `
     -F "name=演示-超上限" -F "file=@samples/ok.csv;type=text/csv" | ConvertFrom-Json
   Start-Sleep -Seconds 3
   (curl.exe -s "http://127.0.0.1:18000/api/v1/jobs/$($big.data.id)" | ConvertFrom-Json).data
   ```
   指出这次终态变成「失败」，错误码 `FILE_TOO_MANY_ROWS`，计数仍是 0 / 0 / 0，且没有新增 `sync_records`。
4. 把 `MAX_RECORDS_PER_JOB` 改回 `10000`，用同一条 `up -d worker` 重建 Worker。**这一步必须当场做完**，否则后续后端测试会失败。

#### 预期画面／结果
- 改动一行配置后，`ok.csv` 从 `SUCCESS` 变为 `FAILED` / `FILE_TOO_MANY_ROWS`。
- `sync_records` 没有写入新行。
- 演示结束时配置已恢复 `10000`，Worker 已重启。

- 报告与截图能对应上刚才演示的三个场景。

## 结尾
- 本次已验证：
  - 创建任务接口立即返回 `PENDING`，端到端实测 196 ms，不等待整份 CSV。
  - 合法数据写入 MySQL：`ok.csv` 为 `SUCCESS` 2 / 2 / 0，`sync_records` 两行与 `samples/README.md` 一致。
  - 非法数据可定位：`row-errors.csv` 为 `PARTIAL_SUCCESS` 8 / 1 / 7 并逐行给出错误码；`bad-header.csv` 与 `empty.csv` 为文件级失败，行号显示 `-`。
  - 业务规则集中在 `MAX_RECORDS_PER_JOB`，改一处配置即可把同一份文件从成功变为 `FILE_TOO_MANY_ROWS`。
  - `pytest` 65 passed，端到端链路与页面检查均有截图留档。
- 当前限制：
  - 不实现登录与权限；不实现失败重试、幂等键、任务取消和错误导出。
  - `WORKER_CONCURRENCY` 未接入，Worker 单进程串行消费，1,000 行并发基线未验证。
  - 超时回收只在 Worker 启动时执行一次，且会误伤 `started_at` 为空的 `RUNNING`。
  - 错误明细排序为 `row_number ASC, id ASC`，空行号（文件级错误）排在最前。
  - 前端没有自动化测试，页面验收靠 `npm run lint`、`npm run build` 与手工走查。
  - 本机宿主端口 8000 落在 Windows 保留区间时，Compose 需用 `docker-compose.e2e.yml` 覆盖为 18000。
- 下一阶段计划：
  - 为前端补关键交互测试（创建、列表、详情三态与轮询停止），见 `docs/week-04/前端测试计划.md`。
  - 接入 `WORKER_CONCURRENCY` 并补 1,000 行并发基线用例。
  - 评估超时回收改为周期执行，并明确回收后已写入记录与计数的处置。
  - 按复盘行动项开启 V1.1 议题：重试策略与执行记录、幂等键与文件摘要、任务取消、CI 自动检查、结果导出。
