# 第 3 周任务计划（CSV 同步闭环 + V1.0 发布）

来源：`docs/tasks/week-03.pdf`（第 3 周：CSV 同步、测试与 V1.0 发布）。
本文只做任务拆分与排期，不改规格；与规格冲突时以 PDF 为准，冲突点集中在最后一节「待拍板」。

目标：完成基础闭环并交付可运行的 V1.0 —— CSV 解析校验 → Redis 投递 → 基础 Worker → MySQL 写入 → 错误记录 → 任务统计 → Web 页面（创建 / 详情刷新 / 错误明细）→ 测试与发布包。

预估口径：1 人 + AI 辅助；`P0` 是 V1 发布必须，`P1` 应做，`P2` 可下移到 V1.1。P0 合计约 50 人时，按 6 个工作日安排。

## 五、待拍板与风险

| # | 事项 | 影响 | 建议 |
| --- | --- | --- | --- |
| 1 | 规格的 12 个错误码里没有「批量写入失败」的码，但要求「单批失败要记清哪批、什么原因」 | 行级错误码集合会被撑大 | 复用已存在的 `INTERNAL_ERROR` 写入 `sync_errors` 与 `last_error_code`，消息带批号；**需确认是否允许新增 `DB_WRITE_FAILED`** |
| 2 | 文件级失败时 `total_records` / `failed_records` 的口径（行级失败行的计数规则） | 统计与前端入口判定 | 建议 `total = success + failed`；文件级失败时 `total = 0`、`failed = 0`，文件级错误只体现在 `last_error_code` 与 `sync_errors` |
| 3 | 由 2 引出：规格里「查看错误明细」入口的触发条件是失败数大于 0；按第 2 条口径文件级失败时失败数为 0，用户点不到明细页 | 用户看不到失败原因 | W3-E4 改为 `failed_records > 0` **或** `status === "FAILED"` 时显示入口 |
| 4 | 错误明细排序 `row_number ASC` 在 MySQL 里 NULL 排最前，文件级错误会插在行级错误前面 | 展示顺序 | 若希望文件级固定排最前/最后，需显式 `ORDER BY (row_number IS NULL) DESC, row_number ASC, id ASC`，**需确认顺序** |
| 5 | `PARTIAL_SUCCESS` 要同时改后端枚举、列表筛选白名单、前端类型与徽章 | 漏改会导致筛选不到、徽章显示英文 | 已同步。列表筛选用例在 `test_list_pagination_boundaries`。错误明细客户端仍属 W3-E6 |
| 6 | 10MB / 10000 行双上限：API 只拦住 10MB，行数上限只能在 Worker 判定 | 大文件绕过前端校验 | W3-A4 在 Worker 内判定；`FILE_TOO_MANY_ROWS` 属文件级失败 |
| 7 | `amount` 用 float 会丢精度，`DECIMAL(12,2)` 还有上限 | 金额校验误判 | 全程 `Decimal`；超过 `DECIMAL(12,2)` 范围按 `AMOUNT_INVALID` 处理 |
| 8 | Worker 崩溃会留下 `RUNNING` 悬挂任务 | 任务永久卡住 | W3-C4（P2）启动回收；不做则写进复盘已知问题 |
| 9 | 范围控制：幂等键、重试退避、导出接口是第 5 周/后续周内容 | 本周膨胀 | 本周不做；`.env` 里的 `MAX_JOB_ATTEMPTS`、`IDEMPOTENCY_KEY_TTL_HOURS` 先留着不接 |
| 10 | 测试库若新增索引/列，需要重新执行迁移 | 集成测试报错 | 表结构本周无变更；若 W3-C4 加索引，同步改 `scripts/init_db.sql` 并重跑 `migrate.ps1 -Test` |
