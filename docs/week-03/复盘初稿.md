## 2. 背景与目标

### 背景

业务人员需要把 CSV 里的商品、订单或运营数据批量导入业务系统。人工录入效率低、容易遗漏；一次性脚本导入虽然快，但通常缺少任务状态、错误明细和重复导入保护。导入失败后，使用者很难判断是文件格式问题、某一行数据不合法，还是系统暂时不可用。

SyncFlow 要提供一条可追踪的导入闭环：用户在 React 页面提交 CSV，系统创建任务并异步处理，逐行校验，把合法数据写入 MySQL，同时保存状态、统计和错误明细。

主要约束：

- 本地可运行：`docker compose up` 拉起 Web / API / Worker / MySQL / Redis 五个服务，核心功能不建在云服务、外部数据库或个人账号上。
- 技术栈统一：后端 Python + FastAPI 或 Go + Gin 二选一（本项目选 Python + FastAPI）；前端 React 18+ / TypeScript / Vite / React Router；MySQL 8.x；Redis 7.x。
- 数据原则：金额用 DECIMAL 不用浮点；时间用 `datetime(3)` 存 UTC；表间不建外键、关联在应用层维护；同一任务内业务标识唯一。
- 接口原则：响应统一信封；不返回内部路径、SQL、堆栈和连接配置；列表接口必须分页。
- 范围：不实现登录与权限，所有功能对所有访问者开放。
- 协作：所有变更走分支 → PR → AI Code Review，不直接推主分支。

### 原定目标

出自第 3 周「V1.0 发布标准」，共 7 条：

1. 用户可以通过 React Web 页面创建任务和查看结果。验收：浏览器可完成创建→详情→错误明细全流程。
2. 创建任务接口不会等待整个 CSV 处理完成。验收：创建响应立即返回，状态为 `PENDING`，处理随后由 Worker 完成。
3. 合法 CSV 数据能够写入 MySQL。验收：`sync_records` 行数与样例期望一致。
4. 非法数据能够查询到行号和错误原因。验收：错误明细接口与页面能看到 `row_number` 和 `error_code`。
5. 任务统计数据准确。验收：样例期望统计 = 页面 / 接口 / 表内统计。
6. 代码经过至少一次 PR 和 AI Code Review。验收：有可独立审阅的 PR 与 Review 记录。
7. 能现场解释并修改一处业务规则。验收：规则集中在一处，演示时改一个配置就能改变行为。

三项产出物（第 3 周「产出物细则」）：

- 异步导入闭环：UTF-8/BOM、表头与字段校验、去重、Redis 投递、Worker 消费、批量事务、统计与错误记录。判定：创建接口快速返回；Worker 可将任务处理至终态；成功和失败数据分别在 MySQL 可查。
- 完整 Web 操作页面：CSV 选择与前端校验、上传状态、任务详情刷新、错误表格和分页。判定：合法文件可创建；非法文件无法提交；运行中状态和错误明细均可在页面查看。
- V1.0 发布包：正常/异常样例、测试报告、部署说明、Release Notes、演示和复盘。判定：空环境可复现版本；样例预期与实际统计一致。

## 4. 做得好的地方

### 业务规则集中到单一配置与单一常量表

- 带来的收益：表头、字段规则、12 个错误码都定义在一处，页面、Worker 和测试不会各写一套；演示时改 `MAX_RECORDS_PER_JOB` 一个值就能改变终态，不用碰校验代码。
- 支持证据：`backend/app/core/error_codes.py` 集中定义文件级 5 码与行级 7 码，由 `test_sync_error_codes_match_week3_spec` 锁住集合与 `field_name`；`Settings.max_records_per_job` 被解析、导入和 Worker 共用，`test_max_records_per_job_reads_env` 验证默认为 10000 且读取环境变量。
- 后续如何复用：V1.1 的导出功能直接复用这套错误码，避免导出口径与页面不一致。

### 创建与导入分离，用队列解耦

- 带来的收益：创建接口只做校验、落盘、写 `PENDING` 和入队就返回，实测 196 ms；10,000 行的解析和写入在 Worker 里做，用户不必等整个文件算完。
- 支持证据：端到端 POST 返回 `PENDING`，随后同一任务在库中变为 `SUCCESS` 2 / 2 / 0；`test_create_job_success` 断言创建只返回 `id/name/status/created_at` 并已入测试队列。
- 后续如何复用：V1.1 加取消和重试时，仍从这条队列边界切入，不改创建接口契约。

### 样例数据 + 期望统计当作可执行的验收口径

- 带来的收益：`samples/` 五份文件各带期望的终态与计数，`test_samples.py` 直接对照断言，发布判定不用靠人肉核对页面数字。
- 支持证据：`ok.csv`、`bom.csv`、`row-errors.csv`、`bad-header.csv`、`empty.csv` 的终态与 `total/success/failed` 全部与 `samples/README.md` 一致；`row-errors.csv` 第 3–9 行的错误码逐行锁定。
- 后续如何复用：V1.1 的新功能沿用「加一份样例、写期望、进测试」的做法。

### 批量事务策略只回滚失败的那一批

- 带来的收益：一批唯一约束冲突不会让整个任务全废，其余批次的数据仍然落库，统计如实反映成功与失败，且消息里保留批号便于定位。
- 支持证据：`test_failed_batch_does_not_roll_back_other_batches` 断言 4 行中冲突 1 批时得到 `PARTIAL_SUCCESS` 与 2 / 2；`test_multiple_batch_failures_summarize_batch_numbers` 验证多批汇总文案。
- 后续如何复用：批大小 200 落在规格建议的 100–500 区间，后续调参只改 `RECORD_BATCH_SIZE`。

### 错误信息对外脱敏有明确边界

- 带来的收益：公开响应里不出现连接串、SQL、堆栈和内部路径，数据库原文只进日志，排障靠日志、对外靠稳定错误码。
- 支持证据：`test_database_error_is_hidden` 断言 500 响应不含 `secret-password`、`mysql+pymysql` 和 `Traceback` 且删除已写文件；`test_worker_unexpected_error_does_not_stay_running` 断言意外异常对外只有「Worker 处理失败」。
- 后续如何复用：V1.1 新增接口沿用同一信封与脱敏约定。

## 5. 问题与原因

### 问题 1：宿主端口 8000 落在 Windows 保留区间，Compose 的 API 无法发布

- 事实：`netsh interface ipv4 show excludedportrange protocol=tcp` 显示保留区间包含 7998–8097，8000 在其中。按 `docker-compose.yml` 原样 `8000:8000` 发布时，`syncflow-api-1` 停在 `Created` 从未启动，mysql、redis、worker 均已 Up。
- 影响：Compose 整条链路无法按默认端口起来，端到端验证一度无法进行；README 6.3 给的换端口方案只适用于宿主机进程，不覆盖 Compose。
- 原因与证据：Windows 的保留端口由系统与 Hyper-V 动态占用，与代码无关；`docker inspect syncflow-api-1` 显示 `created`，`TcpListener` 绑定 8000 返回拒绝访问，而 18000 可绑。
- 已采取的处理：新增 `docker-compose.e2e.yml`，用 `!override` 只把 API 的宿主端口改为 `18000:8000`，容器内端口与 web 的 `API_PROXY_TARGET=http://api:8000` 均不变；`docker-compose.yml` 未改动。端到端据此跑通并留档。
- 遗留问题：该文件已提交但 README 与 Release Notes 都未提及，读者不知道存在这条 Compose 路径；`docker-compose.yml` 的默认端口在同类机器上仍会失败。

- 影响：Release Notes 让读者去测试报告看结果，但标签里那份没有端到端记录，第 3 周「V1.0 发布包」的「空环境可复现」判定缺少标签级证据。
- 原因与证据：端到端验证与报告扩充发生在打标签之后（截图时间 15:37–15:57，发布提交时间更早）；发布流程没有「标签前核对发布包完整性」这一步。

### 问题 4：第 1 周设计文档与最终实现不一致，且未回填

- 事实：第 1 周设计文档用的是 `sku,name,price,quantity` 表头、`job_records` / `job_errors` / `job_attempts` 四张表和 `succeeded` / `partial_succeeded` 状态名；实现最终是 `external_id,name,amount,record_date`、`sync_jobs` / `sync_records` / `sync_errors` 三张表和 `SUCCESS` / `PARTIAL_SUCCESS`。API 设计里还列了 `/records`、`/cancel`、`/export` 和 `VALIDATION_ERROR`、`UNSUPPORTED_MEDIA_TYPE` 等本周未实现的路径与错误码。
- 影响：设计文档作为规格源头已经失真，新人按第 1 周文档读代码会对不上；评审时也无法用设计文档验证实现。
- 原因与证据：第 3 周任务书把表头和字段规则改成了 `external_id,name,amount,record_date`，实现跟的是新任务书，但第 1 周文档没有同步更新；对比 `docs/week-01/06-数据库设计.md` 与 `backend/app/models/`、`docs/week-01/05-API设计.md` 与实际路由即可看出。
- 已采取的处理：第 3 周的 `docs/api.md` 按实际实现重写了接口与错误码，作为当前权威口径。
- 遗留问题：第 1 周的 5 份设计文档仍在仓库中且未标注「已被第 3 周规格取代」。

### 问题 5：测试报告里的核对命令用了 MySQL 保留字

- 事实：测试报告「Worker」一节给的 `SELECT job_id,row_number,error_code FROM sync_errors ...` 会报 `ERROR 1064 (42000)`，因为 `ROW_NUMBER` 是 MySQL 8.0 保留字（`INFORMATION_SCHEMA.KEYWORDS` 中 `RESERVED=1`）。该报错已经出现在留档的 Worker 日志截图里。
- 影响：读者照抄该命令无法执行；那次端到端里查 `sync_errors` 的语句实际未成功，只有 `sync_jobs` 和 `sync_records` 两条查询返回了结果。
- 原因与证据：`ROW_NUMBER` 自 MySQL 8.0 起为保留字，未加反引号会被解析为窗口函数；PowerShell 双引号字符串中反引号又是转义符，直接写 `` `row_number` `` 会被吃掉。
- 已采取的处理：改用不加保留字的列集合（`job_id, field_name, error_code, error_message`），已实测通过。
- 遗留问题：报告正文与 `Worker日志.png` 尚未同步更新。

### 问题 6：`.env` 中的并发与重试配置未接入

- 事实：`WORKER_CONCURRENCY=2`、`MAX_JOB_ATTEMPTS=3`、`RETRY_BACKOFF_SECONDS=5,30,120`、`IDEMPOTENCY_KEY_TTL_HOURS=24` 都在 `.env` 与 `.env.example` 里，但代码中没有任何一处读取。Worker 是单进程 `BRPOP` 串行消费。
- 影响：第 1 周测试计划的「1,000 行并发基线」无法验证；配置文件里存在「看起来生效其实没用」的项，容易误导运维。
- 原因与证据：全仓搜索这些变量只有 `.env` / `.env.example` / 文档命中，`backend/app/` 无引用；`worker.py` 主循环单个 `dequeue_job(timeout=5)`。
- 已采取的处理：在 Release Notes 的「不包含」和 README 第 14 节明确写出这些项保留但 V1.0 不接入。
- 遗留问题：配置项与实际能力的落差靠文档说明弥补，属于 V1.1 议题。

### 问题 7：超时回收只在 Worker 启动时执行一次，且会误伤 `started_at` 为空的 `RUNNING`

- 事实：`reclaim_stale_running` 在 Worker 启动时调用一次；筛选条件是 `started_at IS NULL OR started_at < deadline`，因此 `started_at` 为空的 `RUNNING` 会被立即收成 `FAILED`。回收只改 `sync_jobs`，不删已写入的 `sync_records`，也不重算计数。
- 影响：长时间运行中卡住的 `RUNNING` 不会被自动回收；被回收的任务统计可能与 `sync_records` 实际行数不一致。
- 原因与证据：`worker.py` 只在 `main()` 里调用一次 `reclaim_stale_jobs`；`test_reclaim_stale_running_leaves_fresh_jobs` 验证了超时与新鲜的区分，但没有覆盖 `started_at` 为空的边界。
- 已采取的处理：消息统一为「任务处理超时」，并把该限制写进 README 第 14 节与 Release Notes。
- 遗留问题：是否改为周期回收、以及回收后如何处置已写入记录，留给 V1.1。

### 问题 8：前端错误码常量文件无人引用

- 事实：`frontend/src/api/errorCodes.ts` 镜像了后端 12 个错误码与中文含义，但全 `frontend/src` 无任何 import，生产构建产物里也不含它。页面错误文案实际用的是接口返回的 `error_message`。
- 影响：同一套错误码存在两份定义，改后端容易漏改前端；这个文件让「前后端共用一套码」的说法看起来已落实，实际未生效。
- 原因与证据：grep `errorCodes` 只在该文件自身命中；`npm run build` 产出的 bundle 中搜不到其导出常量。
- 已采取的处理：明确以接口返回的 `error_message` 为准，并在测试报告与 AI Review 中记录。
- 遗留问题：要么接入页面做本地化兜底，要么删除该文件，二选一未定。

## 6. 关键决策与取舍

- **决策 1：文件级失败时 `total / success / failed` 三个计数都为 0。**
  - 当时的依据：第 3 周规格没有写死文件级失败时的计数口径，任务计划建议 `total = success + failed`，文件级错误只体现在 `last_error_code` 与 `sync_errors`。
  - 实际收益与代价：统计口径自洽，代价是「查看错误明细」入口不能只看 `failed_records > 0`，否则文件级失败点不进去。
  - 下次是否调整：口径本身保留；入口条件已相应改为 `failed_records > 0` 或 `status === "FAILED"`，这个联动要一起记住。

- **决策 2：批量写入失败复用 `INTERNAL_ERROR`，不新增 `DB_WRITE_FAILED`。**
  - 当时的依据：规格给的 12 个错误码里没有「批量写入失败」，而要求记清哪批、什么原因；为不撑大错误码集合，复用已有接口错误码并在消息里带批号。
  - 实际收益与代价：错误码集合保持 12 个、与规格逐条对应；代价是 `sync_errors` 里出现了一个非 CSV 语义的码，语义上略有混杂。
  - 下次是否调整：V1.1 可考虑新增 `DB_WRITE_FAILED`，届时需决定已有数据是否保持旧码。

- **决策 3：错误明细排序用 `row_number ASC, id ASC`，空行号排在最前。**
  - 当时的依据：规格只写了 `row_number ASC, id ASC`，未规定空行号位置；MySQL 默认把 NULL 排在前面，直接沿用即可。
  - 实际收益与代价：实现最简、与规格字面一致；代价是文件级错误出现在行级错误之前，顺序上略反直觉（通常想先看具体行）。
  - 下次是否调整：待确认是固定在最后，还是维持现状。

- **决策 4：不改已提交的 `docker-compose.yml` 端口，改用独立覆盖文件。**
  - 当时的依据：README 与复盘都明确「不要改已提交的 Compose 端口」；8000 被系统保留是环境问题，不该污染发布配置。
  - 实际收益与代价：主配置保持原样，端到端可复现；代价是多一个需要说明的配置文件，而文档还没补上它的说明。
  - 下次是否调整：做法保留，但必须同步在 README 与 Release Notes 登记该文件。

- **决策 5：CSV 读取全量进内存，写入分批提交。**
  - 当时的依据：上传上限 10 MB 由 `MAX_UPLOAD_FILE_SIZE_MB` 兜住，内存占用有上界；`csv.reader` 在整段文本上解析最简单，也便于把「文件行号」算准（含表头、空行不计数）。写入按 200 行一批，落在规格建议的 100–500 区间。
  - 实际收益与代价：行号语义清晰、错误定位准确；代价是没有做流式读取，内存占用随文件线性增长（但被封顶在 10 MB）。
  - 下次是否调整：当前规模不必调整；若上限放宽或换更大文件，再改流式。

- **决策 6：金额全程用 `Decimal`，`amount` 校验拒绝科学计数法与超范围。**
  - 当时的依据：规格与 PRD 都要求金额精确、禁用浮点，且 `DECIMAL(12,2)` 有范围上限。
  - 实际收益与代价：`19` / `19.9` / `19.90` 统一归一为两位小数且不丢精度；代价是校验分支变多（负数、小数位、科学计数法、超范围、格式错各一条消息）。
  - 下次是否调整：保留。

- **决策 7：不实现登录与权限，也不实现取消、重试、导出。**
  - 当时的依据：PRD 明确本项目不实现登录与权限；取消、重试、导出属于 V1.1 增强方向。
  - 实际收益与代价：V1.0 范围收敛，3 周内可交付；代价是第 1 周 API 设计里列出的 `/cancel`、`/export` 与 `job_attempts` 表落空，设计文档需要标注取代关系。
  - 下次是否调整：V1.1 按 PRD 增强方向逐项开 Issue。
