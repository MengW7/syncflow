# V1.0 复盘初稿

日期：2026-10-16。范围是 CSV 同步闭环和 V1.0 发布包，不改已经合并的主线行为。

## 做完了什么

解析、批量写入、Worker、错误明细接口和创建 / 详情 / 错误页面已经分开合并。发布包补了五份样例、样例统计测试、10MB 边界、测试报告、README、API 示例、Release Notes 和演示脚本。`pytest` 为 65 passed。标签 `v1.0.0` 指向发布提交，后续 V1.1 从新议题做，不在这个标签上重写主线。

## 顺利的地方

错误码、表头和金额规则集中在后端一处，样例测试可以直接对照 `samples/README.md`。创建接口和导入分开之后，终态统计与 `sync_records`、`sync_errors` 能放在同一个事务里核对。页面的终态轮询和文件级错误入口按实际计数口径做了，文件级失败不会因为失败数是 0 而进不去明细。

## 难点

文件级失败的计数、错误明细里空行号的排序、批量写入失败用哪个错误码，规格没有一次说死。实现按任务计划里的建议落地，并写进 Release Notes，避免页面和测试各用一套口径。

宿主机和 Compose 的上传路径不同。两个 Worker 同时消费 `syncflow:jobs` 时，后一个会把任务标成文件不可读。README 现在明确要求只留一个消费者，并且不要把宿主机的 `UPLOAD_DIR` 写进 `.env`。

本机 Windows 排除了 8000 附近的端口，Compose 按原端口发布 API 会绑失败。文档给出换端口的办法，没有改已提交的 Compose 端口。

## 留下的问题

这些不在 V1.0 里改。当前环境没有 GitHub CLI，议题没有推到远端，下面的正文可以直接新建。

### 批量写入失败是否新增错误码

V1.0 把单批失败记成 `INTERNAL_ERROR`，消息带批号，原始 SQL 只进日志。需要决定要不要新增 `DB_WRITE_FAILED`，以及已有数据是否保持旧码。

### 错误明细空行号的排序

现在是 `ORDER BY row_number ASC, id ASC`，MySQL 把空行号排在最前。需要确认文件级错误要固定在最前、最后，还是维持现状。

### 超时任务的回收不完整

回收只在 Worker 启动时做一次。`started_at` 为空的 `RUNNING` 会立刻被收成失败。已经提交的 `sync_records` 不会删，计数也不会重算，可能和表里的行数不一致。V1.1 再决定是否周期回收，以及失败后的记录怎么处理。

### 幂等、重试和导出

`MAX_JOB_ATTEMPTS`、`RETRY_BACKOFF_SECONDS`、`IDEMPOTENCY_KEY_TTL_HOURS` 还没有接入。取消任务和错误导出也没有。V1.1 不要直接在 `v1.0.0` 上改历史提交。

### 前端自动化和重复常量

前端只有 `npm run lint` 和 `npm run build`，没有测试脚本。上传 10MB 和名称 128 字在页面里写了常量，和后端配置各算各的。`frontend/src/api/errorCodes.ts` 还没有被页面引用，错误文案以接口返回的 `error_message` 为准。
