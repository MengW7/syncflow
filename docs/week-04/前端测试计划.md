# 前端关键交互测试计划（Vitest + React Testing Library）

来源：PRD 9.2「前端工程质量」。承接 `docs/week-03/复盘初稿.md` 问题 3「前端没有自动化测试」。只补前端测试，不动后端和已发布的 V1.0 行为。

## 1. 要求出处与范围

PRD 9.2 原文：

> 前端代码使用 TypeScript；页面、组件、API 客户端和领域类型应有清晰边界。
> 通用逻辑（状态展示、日期格式化、错误提示）应复用，避免在多个页面复制。
> 前端**至少**覆盖创建任务、任务列表和任务详情的关键交互测试。
> 生产构建必须成功，且不允许 TypeScript 类型错误。

这条要求没有进 V1.0 的门槛。对照 PRD 第 10 节「最低要求」逐条看：

| 出处 | 原文 | 是否 V1.0 门槛 |
| --- | --- | --- |
| PRD 9.2 | 前端至少覆盖创建任务、任务列表和任务详情的**关键交互测试** | 非功能需求，明确要求 |
| PRD 10 V1.0 第 5 条 | 有数据库迁移、基础单元测试和 **API 集成测试** | 未提前端测试 |
| PRD 10 V1.0 第 7 条 | 前端具有四个页面，并正确处理加载、空数据和请求失败状态 | 只要求页面存在与三态 |

所以 V1.0 以手工走查替代，本条推到 V1.1。

范围按 PRD 9.2 的「至少」来，即**创建任务、任务列表、任务详情**三个区域。错误明细页不在最低要求内，与 API 客户端、纯函数一起列为可选。

不在范围：端到端测试（理由见第 2 节）；后端测试（已有 65 个用例，见 `docs/week-03/测试报告.md`）；修改任何页面行为，测试暴露出的缺陷另开修复任务。

## 2. 选型与环境

选 **Vitest + React Testing Library**。

| 选项 | 结论 | 依据 |
| --- | --- | --- |
| Vitest | 采用 | 与 Vite 共用配置和转换链；项目是 `"type": "module"`，原生支持 ESM；自带假定时器，3 秒轮询可以直接测 |
| Jest | 不用 | 需要为 ESM + Vite 额外配 babel 或 ts-jest，收益不如 Vitest |
| Playwright / Cypress | 不用 | 属端到端，要真实启动 API + MySQL + Redis；PRD 9.2 要的是关键交互测试 |

实测环境：Node.js v22.14.0、npm 10.9.2、Vite ^8.3.0、React ^19.2.8、TypeScript ~6.0.2，无测试脚本。React 19 需要 `@testing-library/react` v16 及以上。

## 3. 现状与没做的原因

| 项 | 现状 |
| --- | --- |
| `package.json` 脚本 | 只有 `dev`、`build`、`lint`、`preview`，无 `test` |
| 测试框架 | `devDependencies` 里没有 vitest / jest |
| 测试文件 | `frontend/src/` 下无 `*.test.*` |
| 现有兜底 | `npm run lint`、`npm run build`，以及 `docs/week-03/screenshots/` 的三张页面走查截图 |

三周里后端要交 CSV 解析、批量事务、Worker、统计和错误明细，前端要交四个页面，测试预算全给了后端；V1.0 验收标准又不含这条，于是被推到 V1.1。

另有一个技术原因让当时不容易顺手加。`build` 是 `tsc -b && vite build`，而 `tsconfig.app.json` 的 `include` 是 `["src"]`、`types` 只有 `["vite/client"]`。测试文件放进 `src/` 后不补类型声明，`tsc -b` 会先失败。处理方式见 4.4。

## 4. 实施步骤

### 4.1 安装依赖

```powershell
cd frontend
npm i -D vitest jsdom @testing-library/react @testing-library/dom @testing-library/user-event @testing-library/jest-dom
```

RTL v16 把 `@testing-library/dom` 提为 peer 依赖，必须显式装，否则 import 报错。版本号先不写死：装完跑 `npm ls vitest` 确认它与 Vite 8 的 peer 范围兼容，不兼容就降到 Vitest 文档里标注支持 Vite 8 的那一档。

### 4.2 测试配置

新建 `frontend/vitest.config.ts`，用 `mergeConfig` 复用 `vite.config.ts`，别让别名设置两处维护：

```ts
import { mergeConfig, defineConfig } from "vitest/config";
import viteConfig from "./vite.config";

export default mergeConfig(
  viteConfig,
  defineConfig({
    test: {
      environment: "jsdom",
      globals: true,
      setupFiles: ["./src/test/setup.ts"],
      css: false,
    },
  }),
);
```

新建 `frontend/src/test/setup.ts`：

```ts
import "@testing-library/jest-dom/vitest";
```

子路径必须是 `/vitest`，用主入口不会注册 matcher。

### 4.3 npm 脚本

在 `package.json` 的 `scripts` 加两条：

```json
"test": "vitest run",
"test:watch": "vitest"
```

`test` 用 `run`，默认的 watch 模式在 CI 或非交互终端里会挂住。

### 4.4 `tsc -b` 的类型检查

`tsconfig.app.json` 的 `include` 是 `["src"]`，`types` 是 `["vite/client"]`，测试文件在 `src/` 下会被检查。两个方案：

**A（改动最小）**：把 `types` 改成

```json
"types": ["vite/client", "vitest/globals", "@testing-library/jest-dom"]
```

`npm run build` 仍能通过，测试文件也受类型检查保护。

**B（构建链路更纯）**：在 `tsconfig.app.json` 的 `exclude` 里排除 `**/*.test.ts`、`**/*.test.tsx`、`src/test`，另建 `tsconfig.test.json`，CI 单独跑 `tsc -p tsconfig.test.json --noEmit`。代价是多维护一个配置文件。

### 4.5 目录与组织

测试文件就近放，命名 `*.test.tsx` / `*.test.ts`：

```text
frontend/src/
├── api/client.test.ts
├── components/CreateJobForm.test.tsx
├── hooks/useJobPolling.test.tsx
├── pages/JobListPage.test.tsx
├── pages/JobDetailPage.test.tsx
└── pages/JobErrorsPage.test.tsx
```

### 4.6 打桩策略

| 测试对象 | 策略 | 理由 |
| --- | --- | --- |
| `api/client.ts` | 不替换模块，替换全局 `fetch`（`vi.stubGlobal`） | `client.ts` 直接调全局 `fetch`，这样能真正验证 URL 拼接、信封解析和 `ApiError` 映射 |
| 页面与组件 | 替换 `api/client` 模块（`vi.spyOn` 或 `vi.mock`） | 免得每个用例都去匹配 URL 字符串，脆性最低 |

## 5. 用例清单

### 5.1 创建任务（`CreateJobForm`）

覆盖 `docs/tasks/week-03.pdf`「创建任务页（/jobs/new）」6 条。

| 用例 | 断言 | 规格对应 |
| --- | --- | --- |
| 选择 `.txt` 文件 | 显示「只支持 .csv 文件」；提交后 `createJob` 未被调用 | 只让选 .csv；前端拦截 |
| 文件超过 10MB | 显示「文件不能超过 10MB」；`createJob` 未被调用 | 超过 10MB 前端不让提交 |
| 任务名称超过 128 字符 | 显示「任务名称最长 128 个字符」；`createJob` 未被调用 | 任务名称选填，最多 128 字符 |
| 选择合法文件 | 显示「已选择 <文件名>（<大小>）」 | 选完文件显示文件名和大小 |
| 提交进行中 | 按钮文案「正在创建…」且 `disabled` | 提交过程中按钮置灰 |
| 后端返回失败 | 显示后端 `message`，已填名称与已选文件仍在 | 失败别把用户填的东西清掉 |
| 创建成功 | `onCreated` 收到 `result.data` | 创建成功跳任务详情页 |
| 未选文件直接提交 | 显示「请选择 CSV 文件」 | 缺文件要有明确提示 |

10MB 那条不要真构造 10MB 文件，否则每个用例多花几百毫秒，用属性覆盖即可：

```ts
const big = new File(["x"], "big.csv", { type: "text/csv" });
Object.defineProperty(big, "size", { value: 10 * 1024 * 1024 + 1 });
```

组件里的常量是 `MAX_UPLOAD_BYTES = 10 * 1024 * 1024` 和 `MAX_NAME_LENGTH = 128`，断言文案时对着这两个值看。

### 5.2 任务列表（`JobListPage`）

覆盖 `docs/tasks/week-02.pdf`「任务列表页（/）」6 条 + 通用要求。

| 用例 | 断言 | 规格对应 |
| --- | --- | --- |
| 初次加载 | `listJobs` 收到 `{page: 1, pageSize: 20, status: undefined}` | 首次加载调用列表接口 |
| URL 带状态筛选 | 以 `/?status=PENDING` 渲染时 `listJobs` 收到 `status: "PENDING"` | 筛选条件与 URL 查询参数同步 |
| 切换状态下拉 | `listJobs` 收到 `status: "SUCCESS"`，且 `page` 回落为 1 | 切换页码时保留筛选状态 |
| 空数据 | `total = 0` 时显示「还没有任务。」与「创建任务」入口 | 没任务时显示空状态 |
| 请求失败 | 显示错误消息与「重试」按钮；点击后重新发起请求 | 网络挂了显示重试按钮 |
| 非法页码 | `/?page=0` 时显示「页码不正确」，且不发接口请求 | 通用要求：处理请求失败状态 |
| 非法状态值 | `/?status=NOPE` 时显示「不支持的任务状态」 | 状态枚举白名单 |
| 分页按钮禁用 | 第一页「上一页」`disabled`；总数不足一页时「下一页」`disabled` | 分页边界 |

`PAGE_SIZE` 在页面里是 20。

### 5.3 任务详情与轮询（`JobDetailPage` / `useJobPolling`）

覆盖 `docs/tasks/week-03.pdf`「任务详情页状态刷新」3 条 + `docs/week-02.pdf`「任务详情页」4 条。

这一区域最该先做，锁的是规格里最容易回归的两条。

| 用例 | 断言 | 规格对应 |
| --- | --- | --- |
| 非终态轮询 | 假定时器推进 3 秒后发起第二次请求 | 非终态每 3 秒轮询一次 |
| 终态停止轮询 | 状态变 `SUCCESS` 后再推进 9 秒，`getJob` 调用次数不再增加 | 任务到终态一定把轮询停掉 |
| 卸载清理定时器 | 卸载后推进 3 秒，无新请求 | 页面卸载或切路由要停掉轮询 |
| 文件级失败仍显示入口 | `status: "FAILED"` 且 `failed_records: 0` 时有「查看错误明细」 | 见下方说明 |
| 失败数大于 0 显示入口 | `failed_records: 1` 时有「查看错误明细」 | 失败数大于 0 给入口 |
| 成功且无错误不显示入口 | `SUCCESS` 且 `failed_records: 0` 时无「查看错误明细」 | 反向断言，防误显 |
| 404 | 显示「任务不存在」与返回列表入口 | job_id 不存在显示任务不存在 |
| 加载中 | 显示「正在加载任务…」 | 每个页面处理加载中状态 |
| 刷新失败但已有数据 | 显示「刷新失败：<消息>」，同时保留已有详情 | 请求失败不清空已展示内容 |

「文件级失败仍显示入口」这条来自第 3 周任务计划「待拍板」第 3 条。按计数口径，文件级失败时 `failed_records` 为 0，只看 `failed_records > 0` 点不进错误明细，所以实现写成 `failed_records > 0` **或** `status === "FAILED"`。这个条件在后续重构里很容易被改回单条件，值得用测试锁住。

轮询用例断言落在 `getJob` 的**调用次数**上，别依赖 DOM 渲染时机：

```ts
vi.useFakeTimers();
const getJob = vi.spyOn(client, "getJob")
  .mockResolvedValueOnce({ data: { status: "RUNNING" } } as never)
  .mockResolvedValueOnce({ data: { status: "SUCCESS" } } as never);

const { result } = renderHook(() => useJobPolling("j1"));
await act(async () => { await vi.advanceTimersByTimeAsync(0); });
expect(result.current.job?.status).toBe("RUNNING");

await act(async () => { await vi.advanceTimersByTimeAsync(3000); });
expect(result.current.job?.status).toBe("SUCCESS");

await act(async () => { await vi.advanceTimersByTimeAsync(9000); });
expect(getJob).toHaveBeenCalledTimes(2);
```

hook 里 `POLL_INTERVAL_MS` 是 3000，`TERMINAL` 集合是 `SUCCESS` / `PARTIAL_SUCCESS` / `FAILED` 三个，测试的推进步长按这两个值算。

## 6. 实现注意点

**RTL 的自动 cleanup 依赖全局 `afterEach`。** 如果 `globals: false`，cleanup 会失效，用例之间 DOM 残留，查询会命中多个元素。要么 `globals: true`，要么在 setup 里显式 `afterEach(cleanup)`。

**jest-dom 必须从 `/vitest` 子路径导入。** 写成 `import "@testing-library/jest-dom"` 不注册 matcher，`toBeInTheDocument` 会报未定义。

**假定时器和 `user-event` 一起用会冲突。** 确需同时用要 `userEvent.setup({ advanceTimers: vi.advanceTimersByTime })`。轮询测试和表单测试分开放在不同文件，各自只用一种，最省事。

**改完 `package.json` 要重跑 `build` 和 `lint`。** `tsc -b` 会因缺 `types` 失败；`eslint.config.js` 的 `languageOptions.globals` 目前只设了 `globals.browser`，测试文件里的 `describe` / `it` / `expect` 会被判成 `no-undef`。两种处理：在 `eslint.config.js` 给测试文件追加一段配置，补上 vitest 全局；或者在测试文件里显式 `import { describe, it, expect, vi } from "vitest"`，不依赖隐式全局。

**端到端测试不要混进来。** 用 Compose 拉起 API 再跑前端测试会同时拖慢本地和 CI，PRD 9.2 也不要求。现有手工走查加截图已覆盖发布演示场景。

**`vite build` 不会把测试文件打进产物。** 只有被入口引用的模块才进 bundle，产物体积不受影响，不需要额外配排除。

## 9. 工时与优先级

| 阶段 | 内容 | 估时 |
| --- | --- | --- |
| 工具链 | 安装依赖、新增配置与脚本、改 tsconfig 与 eslint | 1.5h |
| 区域 1 创建表单 | 8 个用例，纯本地逻辑 | 1.5h |
| 区域 2 列表页 | 8 个用例，URL 同步与三态 | 2h |
| 区域 3 详情与轮询 | 9 个用例，假定时器，工作量最大 | 2.5h |
| 区域 4 加分项 | client、错误明细页、纯函数 | 1.5h |
| 文档同步 | 第 8 节三处 | 1h |
| **合计** | 满足 PRD 9.2「至少」范围约 **6–7h**；四个区域做满约 **9–10h** | |

资源紧张时按 **区域 3 → 区域 1 → 区域 2 → 区域 4** 的顺序保留。区域 3 的轮询停止与文件级失败入口是全项目最易回归、又最难靠肉眼验收的逻辑；区域 1 是纯本地校验，最省事；区域 2 的主要护栏是 URL 同步；区域 4 可往后放。

如果 V1.1 仍排不上这条，把它与 PRD 第 10 节 V1.1 增强方向第 4 条「CI 自动执行格式化、静态检查、测试和构建」合成一个议题。测试跑起来后接 CI 是自然的下一步，分开提会重复。
