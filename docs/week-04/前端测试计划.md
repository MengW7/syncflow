# 前端关键交互测试计划（Vitest + React Testing Library）

来源：`docs/PRD/product-requirements.pdf` 第 9.2 节「前端工程质量」。承接 `docs/week-03/复盘初稿.md` 问题 3「前端没有自动化测试」。

本文只覆盖前端测试补建，不改动后端与已发布的 V1.0 行为。

## 1. 背景与范围

### 1.1 要求出处

PRD 9.2 前端工程质量原文要求：

> 前端代码使用 TypeScript；页面、组件、API 客户端和领域类型应有清晰边界。
> 通用逻辑（状态展示、日期格式化、错误提示）应复用，避免在多个页面复制。
> 前端**至少**覆盖创建任务、任务列表和任务详情的关键交互测试。
> 生产构建必须成功，且不允许 TypeScript 类型错误。

对照 V1.0 验收标准（PRD 第 10 节）逐条核对：

| 出处 | 原文 | 是否 V1.0 验收门槛 |
| --- | --- | --- |
| PRD 9.2 | 前端至少覆盖创建任务、任务列表和任务详情的**关键交互测试** | 非功能需求，明确要求 |
| PRD 10 V1.0 第 5 条 | 有数据库迁移、基础单元测试和 **API 集成测试** | 未提前端测试 |
| PRD 10 V1.0 第 7 条 | 前端具有四个页面，并正确处理加载、空数据和请求失败状态 | 只要求页面存在与三态，未要求自动化 |

结论：该要求来自 PRD 9.2，但未被列入 V1.0 验收标准清单，因此 V1.0 以手工走查替代。本计划用于在 V1.1 补上。

PRD 9.2 的措辞是「至少」三个区域：**创建任务、任务列表、任务详情**。错误明细页不在最低要求内。

本计划把错误明细页、API 客户端与纯函数列为可选加分项，不计入最小达标判定。

## 2. 技术选型

### 2.1 选型结论

**Vitest + React Testing Library（RTL）**。

### 2.2 选型理由

| 选项 | 判断 | 依据 |
| --- | --- | --- |
| **Vitest** | 采用 | 与 Vite 共用配置与转换链，无需额外构建配置；项目是 `"type": "module"`，Vitest 原生支持 ESM；自带假定时器，可测 3 秒轮询 |
| Jest | 不采用 | 需为 ESM + Vite 额外配置 babel 或 ts-jest，收益低于 Vitest |
| Playwright / Cypress | 不采用 | 属端到端，需真实启动 API + MySQL + Redis；PRD 9.2 要求的是关键交互测试，不是端到端 |

### 2.3 环境事实（本计划据此编写）

| 项 | 实测值 |
| --- | --- |
| Node.js | v22.14.0 |
| npm | 10.9.2 |
| Vite | ^8.3.0 |
| React | ^19.2.8 |
| TypeScript | ~6.0.2 |
| 测试脚本 | 无 |

React 19 要求 `@testing-library/react` v16 及以上。

## 3. 缺口成因分析

1. **工具链从未初始化**：`package.json` 无测试脚本，`devDependencies` 无测试框架，`src/` 下无测试文件。
2. **范围挤压**：3 周内后端要交付 CSV 解析、批量事务、Worker、统计与错误明细，前端要交付 4 个页面；测试预算全部给了后端（65 个用例）。
3. **验收口径未倒逼**：V1.0 验收标准不含前端测试，PRD 9.2 又不在该清单内，于是被推到 V1.1。
4. **存在一个隐藏障碍**：`build` 脚本是 `tsc -b && vite build`，而 `tsconfig.app.json` 的 `include` 是 `["src"]` 且 `types` 只有 `["vite/client"]`。测试文件放进 `src/` 后若不补类型声明，`tsc -b` 会先失败——这也是当初没顺手加测试的可能原因之一。处理方式见第 4.4 节。

## 4. 实施步骤

### 4.1 安装依赖

```powershell
cd frontend
npm i -D vitest jsdom @testing-library/react @testing-library/dom @testing-library/user-event @testing-library/jest-dom
```

注意事项：

- RTL v16 把 `@testing-library/dom` 提升为 peer 依赖，必须显式安装，否则 import 报错。
- 本文不指定版本号。项目使用较新的 Vite 8 与 React 19，安装后先执行 `npm ls vitest` 确认与 Vite 8 的 peer 范围兼容；不兼容则降到 Vitest 官方文档标注支持 Vite 8 的那一档。

### 4.2 新增测试配置

新建 `frontend/vitest.config.ts`，用 `mergeConfig` 复用 `vite.config.ts`，避免别名等设置两处维护：

```ts
import { mergeConfig, defineConfig } from "vitest/config";
import viteConfig from "./vite.config";

export default mergeConfig(
  viteConfig,
  defineConfig({
    test: {
      environment: "jsdom",
      globals: true,
      setupFiles: ["./src/test/setup.ts"],
      css: false,
    },
  }),
);
```

新建 `frontend/src/test/setup.ts`：

```ts
import "@testing-library/jest-dom/vitest";
```

必须使用 `/vitest` 子路径。用主入口不会注册 matcher。

### 4.3 新增 npm 脚本

在 `package.json` 的 `scripts` 增加：

```json
"test": "vitest run",
"test:watch": "vitest"
```

`test` 使用 `run` 而非默认 watch 模式，否则 CI 或非交互终端会挂住。

### 4.4 处理 `tsc -b` 的类型检查

`tsconfig.app.json` 的 `include` 是 `["src"]`，`types` 是 `["vite/client"]`。测试文件在 `src/` 下会被检查，需要补类型。

**方案 A（推荐，改动最小）**：把 `tsconfig.app.json` 的 `types` 改为

```json
"types": ["vite/client", "vitest/globals", "@testing-library/jest-dom"]
```

这样 `npm run build` 仍能通过，测试文件也受类型检查保护。

**方案 B（构建链路更纯）**：在 `tsconfig.app.json` 的 `exclude` 中排除 `**/*.test.ts`、`**/*.test.tsx`、`src/test`，另建 `tsconfig.test.json`，并在 CI 单独执行 `tsc -p tsconfig.test.json --noEmit`。代价是多维护一个配置文件。

### 4.5 目录与组织

测试文件就近放置，命名 `*.test.tsx` / `*.test.ts`：

```text
frontend/src/
├── api/client.test.ts
├── components/CreateJobForm.test.tsx
├── hooks/useJobPolling.test.tsx
├── pages/JobListPage.test.tsx
├── pages/JobDetailPage.test.tsx
└── pages/JobErrorsPage.test.tsx
```

### 4.6 打桩策略

| 测试对象 | 策略 | 理由 |
| --- | --- | --- |
| `api/client.ts` | 不替换模块，替换全局 `fetch`（`vi.stubGlobal`） | `client.ts` 直接调用全局 `fetch`；这样能真正验证 URL 拼接、信封解析与 `ApiError` 映射 |
| 页面与组件 | 替换 `api/client` 模块（`vi.spyOn` 或 `vi.mock`） | 避免每个用例都去匹配 URL 字符串，脆性最低 |

## 5. 用例清单

### 5.1 区域 1 · 创建任务（`CreateJobForm`）

覆盖规格：`docs/tasks/week-03.pdf`「创建任务页（/jobs/new）」6 条。

| 用例 | 断言 | 规格对应 |
| --- | --- | --- |
| 选择 `.txt` 文件 | 显示「只支持 .csv 文件」；提交后 `createJob` 未被调用 | 只让选 .csv；前端拦截 |
| 文件超过 10MB | 显示「文件不能超过 10MB」；`createJob` 未被调用 | 超过 10MB 前端不让提交 |
| 任务名称超过 128 字符 | 显示「任务名称最长 128 个字符」；`createJob` 未被调用 | 任务名称选填，最多 128 字符 |
| 选择合法文件 | 显示「已选择 <文件名>（<大小>）」 | 选完文件显示文件名和大小 |
| 提交进行中 | 按钮文案为「正在创建…」且 `disabled` | 提交过程中按钮置灰 |
| 后端返回失败 | 显示后端 `message`，且已填名称与已选文件未被清空 | 失败别把用户填的东西清掉 |
| 创建成功 | `onCreated` 收到 `result.data` | 创建成功跳任务详情页 |
| 未选择文件直接提交 | 显示「请选择 CSV 文件」 | 缺文件应当有明确提示 |

实现要点：10MB 用例不要真的构造 10MB 文件，否则每个用例多耗数百毫秒。用属性覆盖：

```ts
const big = new File(["x"], "big.csv", { type: "text/csv" });
Object.defineProperty(big, "size", { value: 10 * 1024 * 1024 + 1 });
```

### 5.2 区域 2 · 任务列表（`JobListPage`）

覆盖规格：`docs/tasks/week-02.pdf`「任务列表页（/）」6 条 + 通用要求。

| 用例 | 断言 | 规格对应 |
| --- | --- | --- |
| 初次加载 | `listJobs` 收到 `{page: 1, pageSize: 20, status: undefined}` | 首次加载调用列表接口 |
| URL 带状态筛选 | 以 `/?status=PENDING` 渲染时 `listJobs` 收到 `status: "PENDING"` | 筛选条件与 URL 查询参数同步 |

### 5.3 区域 3 · 任务详情与轮询（`JobDetailPage` / `useJobPolling`）

覆盖规格：`docs/tasks/week-03.pdf`「任务详情页状态刷新」3 条 + `docs/week-02`「任务详情页」4 条。

本区域优先级最高，锁的是规格中最易回归的两条。

| 用例 | 断言 | 规格对应 |
| --- | --- | --- |
| 非终态轮询 | 假定时器推进 3 秒后发起第二次请求 | 非终态每 3 秒轮询一次 |
| 终态停止轮询 | 状态变 `SUCCESS` 后再推进 9 秒，`getJob` 调用次数不再增加 | 任务到终态一定把轮询停掉 |
| 卸载清理定时器 | 卸载后推进 3 秒，无新请求 | 页面卸载或切路由要停掉轮询 |
| 文件级失败仍显示入口 | `status: "FAILED"` 且 `failed_records: 0` 时有「查看错误明细」 | 见下方说明 |
| 失败数大于 0 显示入口 | `failed_records: 1` 时有「查看错误明细」 | 失败数大于 0 给入口 |
| 成功且无错误不显示入口 | `SUCCESS` 且 `failed_records: 0` 时无「查看错误明细」 | 反向断言，防误显 |
| 404 | 显示「任务不存在」与返回列表入口 | job_id 不存在显示任务不存在 |
| 加载中 | 显示「正在加载任务…」 | 每个页面处理加载中状态 |
| 刷新失败但已有数据 | 显示「刷新失败：<消息>」，同时保留已有详情 | 请求失败不清空已展示内容 |

**关于「文件级失败仍显示入口」**：这是第 3 周任务计划「待拍板」第 3 条的偏离项。按计数口径，文件级失败时 `failed_records` 为 0，仅凭 `failed_records > 0` 会点不进错误明细，因此实现改为 `failed_records > 0` **或** `status === "FAILED"`。该条件最容易在后续重构中被误改回单条件，最值得自动化锁住。

轮询用例的实现要点：断言落在 `getJob` 的**调用次数**上，不要依赖 DOM 渲染时机。

```ts
vi.useFakeTimers();
const getJob = vi.spyOn(client, "getJob")
  .mockResolvedValueOnce({ data: { status: "RUNNING" } } as never)
  .mockResolvedValueOnce({ data: { status: "SUCCESS" } } as never);

const { result } = renderHook(() => useJobPolling("j1"));
await act(async () => { await vi.advanceTimersByTimeAsync(0); });
expect(result.current.job?.status).toBe("RUNNING");

await act(async () => { await vi.advanceTimersByTimeAsync(3000); });
expect(result.current.job?.status).toBe("SUCCESS");

await act(async () => { await vi.advanceTimersByTimeAsync(9000); });
expect(getJob).toHaveBeenCalledTimes(2);
```

## 6. 已知坑位

1. **`globals: false` 会让 RTL 的自动 cleanup 失效**。它依赖全局 `afterEach`。要么设置 `globals: true`，要么在 setup 文件中显式 `afterEach(cleanup)`。否则用例间 DOM 残留，查询会命中多个元素。

2. **jest-dom 必须从 `/vitest` 子路径导入**。写成 `import "@testing-library/jest-dom"` 不会注册 matcher，`toBeInTheDocument` 会报未定义。

3. **假定时器与 `user-event` 同时使用会冲突**。如确需同时使用，需 `userEvent.setup({ advanceTimers: vi.advanceTimersByTime })`。建议把轮询测试与表单测试分置不同文件，各自只用一种。

4. **修改 `package.json` 后必须重跑 `build` 与 `lint`**。`tsc -b` 会因缺 `types` 而失败；`eslint.config.js` 的 `languageOptions.globals` 目前只设了 `globals.browser`，测试文件使用的 `describe` / `it` / `expect` 等全局会被判为 `no-undef`。两种处理方式：
   - 在 `eslint.config.js` 为测试文件追加一段配置，指定 `globals: { ...globals.browser, ...globals.node }` 并补 vitest 全局；
   - 或在测试文件中显式 `import { describe, it, expect, vi } from "vitest"`，不依赖隐式全局。

5. **不要把端到端测试混入**。用 Docker Compose 拉起 API 再跑前端测试会同时拖慢本地与 CI，且 PRD 9.2 不要求。现有手工走查加截图已覆盖发布演示场景。

6. **`vite build` 不会把测试文件打进产物**。只有被入口引用的模块才进 bundle，因此产物体积不受影响。无需额外配置排除。
